The tool behind the numbers

I built a small calibration tool for this: load replies, write pass/fail criteria, label a sample, and see how far the judge agrees with you on replies it never tuned on. The walkthrough replays stored results, so it makes no API calls.

What was tested

A made-up furniture shop, Sofa So Good, with a one-page support policy. {{n testSet.replies}} customer messages and support replies, written by an OpenAI model from a scenario per item and each checked by hand, so the judge never grades its own maker's writing. {{n testSet.cleanReplies}} replies are clean; the rest each carry one planted flaw ({{n testSet.failuresPerCriterion}} per criterion), such as a wrong return window, a missed safety escalation, or a curt brush-off. Another {{n testSet.injections}} replies hide an instruction aimed at the judge, to see whether it obeys.

The judge, {{text models.sonnet.label}} (chosen from three models, below), graded each reply on four criteria, each judging one thing:

  • {{text testSet.criteria.0.name}}: what the reply says matches the policy.
  • {{text testSet.criteria.1.name}}: every question is addressed.
  • {{text testSet.criteria.2.name}}: cases the policy sends to a specialist are handed over, and others aren't.
  • {{text testSet.criteria.3.name}}: polite, plain, no blame.

Every verdict had to quote the reply as evidence. If the quote wasn't really in the text, the score was withheld.

2 Vague criteria: catch rate lies

I ran the same replies against a deliberately vague version of the four criteria ("The reply is accurate", "The reply is helpful", and so on). I expected it to catch fewer failures. It caught slightly more.

It got there by failing almost everything: {{n full.vague.overFailed}} verdicts the answer key passes, against {{n full.good.overFailed}} with clear criteria. A judge that fails every reply catches every failure, so catch rate rewards exactly this mistake. Agreement beyond chance exposes it:

3 How many labels before you can trust it

To check a judge fairly, part of your labels must be held back: the judge's instructions are tuned on some, and it is measured only on the rest. A decision needs at least 5 held-back failures per criterion and a catch-rate range no wider than 30 points. Using the tool's own random draw:

{{block labelsTable}}

Labelling {{n labelsNeeded.0.labels}} replies, a common first instinct, holds back only {{n labelsNeeded.0.heldBack}}, too few failures on every criterion to decide anything. In real data failures are often rarer still, so the number needed is driven by how many failures you can hold back, not by how many replies you label.

What to take away

  • Write criteria that each judge one thing, and measure agreement, not just catch rate.
  • Count held-back failures, not labelled replies.
  • The most expensive model isn't automatically the right judge. {{text models.opus.label}} agreed with the key slightly more than {{text models.sonnet.label}} (kappa {{k models.opus.kappa}} against {{k models.sonnet.kappa}}) at {{times derived.opusVsSonnet}} the cost per reply. Both cleared every bar, so the extra spend bought little here. {{text models.haiku.label}} was by far the cheapest ({{text models.sonnet.label}} cost {{times derived.sonnetVsHaiku}} as much per reply) and caught every planted failure, but obeyed a hidden instruction: the failure that matters most when the replies you grade come from outside. Choose the cheapest model that clears every bar you set before looking, including a safety bar, and check again when the task changes.

Running it at scale

The test was small on purpose. The tool was built for the volumes a real product produces, and the {{n scale.calls}} judge calls on the full test set show how it would behave, and what would give way first.

Cost grows with replies, not with the policy

The policy and the criteria are the same on every call, so the tool sends them in a form the API can cache and reuse: {{pct scale.cacheShare}} of input tokens came from the cache. Without that, the same runs would have cost {{times scale.cacheSaving}} as much. With caching, most of the bill ({{pct scale.outputShare}}) pays for the judge's quote and reason, about {{n scale.outputTokens}} tokens a verdict. A longer policy barely moves the cost; the number of replies does, which is why the monthly figure in the model picker is predictable.

Labels grow with how rare failures are, not with volume

Even a judge that catches every held-back failure needs {{n scale.minFailures}} of them before its range is narrow enough to decide. With a third of labels held back, that puts a floor under labelling that has nothing to do with how many replies you grade:

Grading 1,000 replies a month or 1,000,000 takes the same labels. Rare failures are what make checking a judge expensive, so for a rare failure it can be cheaper to plant examples, as this test did, than to wait for real ones.

Safeguards that let it run unattended

Of {{n scale.calls}} calls, {{n scale.retried}} needed a retry. {{n scale.unclear}} verdicts came back "unclear" and went to a review pile, and the quote check withheld {{n scale.withheld}}. These were in the tool from its first version:

  • A hard spending cap. Before each call the tool sets aside the most that call could cost, so a run stops before it passes the cap ({{usd scale.defaultCap}} by default), not after.
  • Resume, not restart. A stopped run keeps its finished results and sends only what's missing.
  • Backing off when the API is busy. Rate-limit and server errors wait the time the API asks for, then retry.
  • Checks that need no reader. The quote check and the "unclear" answer keep bad verdicts out of the figures without anyone reading every reply.

What would give way first

  • The {{n scale.maxRows}}-row limit. The tool runs in the browser and holds everything in memory. Bigger jobs would move to a server that works through a queue, stores results as it goes, and sends work that can wait as batches.
  • The API key sits in the visitor's browser. That's fine for one person checking their own data. A team would need a server that holds the key and sets a spending limit per person.
  • No speed figures. I didn't record how long calls took, so I make no claim about throughput. It's the first thing I'd measure before a larger run.

Limits

  • One made-up shop, one policy, one person. I wrote the answer key; my blind labels are the only independent check on it.
  • Planted failures are clearer than real ones. Real replies fail in subtler, mixed ways, so expect lower agreement on real data.
  • The criteria overlap at the edges. A reply that keeps a specialist case to itself is sometimes also failed on accuracy. I didn't tune the criteria further against this test set, to keep the figures honest.
  • One bar was replaced after the fact. The original vague-criteria bar expected a lower catch rate; it was missed. Its replacement was fixed before the last {{n full.vagueNew.caught.n}} planted failures were judged, and it passes on those.
